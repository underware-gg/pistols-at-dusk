# 0014 - Tile Membership Is Plural; Category Is a Single Primary Grouping

- Status: accepted
- Scope: Ingestion–Runtime Separation Phase 3 (semantic catalogue flow-through) — tile semantic model
- Extends: [0013](0013-content-keyed-semantics-and-legacy-metadata-layer.md)
- Related: [0005](0005-runtime-tile-genesis-and-provenance.md), [0009](0009-composition-asset-model.md), [0012](0012-runtime-owns-pixels-atomic-assets-synthetic-sheets.md)

## Context

ADR 0013 narrowed the content-keyed semantic catalogue to clean visual facts and preserved the remaining legacy/context/provenance fields as a marked per-physical-tile layer. Two of those moved-out fields — `category` and `layer` — are single-valued `str` fields that, on inspection, each conflate two different concerns:

- **Membership / kind / use** — what a tile *is* and what it can be *used for*. This is multi-valued by nature: a tile can be a `door` and an `arch`; a recolour intended as grass can also serve as a tavern floor or a wall; a bed can be a bench. The legacy data already shows this — a single tile is `category="door"` while its `tags` carry `category:structure` and its `semantics` carry `["door","arch"]`. The single `category`/`layer` fields could only name one value, so the rest of the multiplicity already lived in the plural fields.
- **Canonical home / primary grouping** — where a tile lives in *the* in-engine sheet, and which entity-template collection it belongs to. This is single by nature: a tile occupies one cell on the canonical atlas, and `category` is already the one consumer that matters (`entity_template_from_placeable` uses it as the entity `collection_id`, one-per-tile).

Investigation of current usage confirmed the asymmetry: `layer` (values `map`/`sprite`/`ui`) is **runtime-inert** — nothing in rendering or composition reads `tile.layer`; it is only serialised and exported. `category`'s only load-bearing runtime use is the single-valued entity `collection_id`. The bootstrap collision analysis (ADR 0013) showed both fields *varying across identical-pixel tiles* — i.e. assigned per placement, not per content — precisely because a single field cannot hold the plural membership the data actually carries.

(Distinct from `tile.layer`: the scene **render layer** that drives draw order — `water`/`terrain`/`architecture`/`actors`/`hud`, `DEFAULT_LAYER_ORDER` — comes from scene templates and entity requests, not from `tile.layer`. They are unrelated concepts that happen to share the word.)

## Decision

Separate the two concerns: membership is plural and lives in the plural fields; `category` is a single primary grouping.

- **Plural membership lives in the plural fields.** What a tile is, the themes it belongs to, and the uses it affords are carried by `semantics` and `tags` (both `tuple[str, ...]`), and — for runtime-authored uses — `affordances` and `alt_uses` (ADR 0013's runtime-authored layer). These are many-per-tile by design and are the query / themed-export / agent-procgen surface. Multi-membership is modelled here, **not** by making `category` multi-valued.
- **`layer` is migrated into `tags` and removed as a standalone runtime field.** Its `map`/`sprite`/`ui` value, where useful, becomes a tag (e.g. `layer:map`). It is runtime-inert, so nothing depends on it as a field; the original value remains preserved in the legacy metadata layer (ADR 0013) regardless.
- **`category` is retained (name kept) and reconceived as a single primary grouping / canonical home.** It is one-per-tile, authored (or set by an explicit convention) rather than derived from the unordered plural fields, and it is **not** a "kind" (kinds are plural, in `semantics`). Its jobs are the tile's canonical home on the in-engine sheet and its entity-template `collection_id`.

**Single and plural coexist; neither is redundant.** A *canonical* "here are the tiles" sheet packs by the single primary grouping, so each tile appears once with one home. *Themed* sheets ("all outdoor tiles", "all building structures") are **derived views generated by querying the plural fields** — a tile lands in multiple themed sheets because it *matches multiple queries*, not because it has multiple `category` values. Making `category` plural would re-merge it into `semantics`/`tags` (duplicating the membership already modelled there) and destroy the single-canonical-home property the engine and the canonical packer rely on.

## Consequences

- The runtime tile model: `category` stays as a single primary grouping; `layer` is removed as a field (its value migrates to `tags`); `semantics`/`tags`/`affordances`/`alt_uses` carry all membership.
- The synthetic-sheet packer (ADR 0012) evolves accordingly: the canonical sheet is organised by the single primary grouping; themed/derived sheets are produced by querying the plural fields. Agent-driven procedural generation reasons over the plural fields.
- The legacy metadata layer (ADR 0013) still preserves the original `category` and `layer` values verbatim, so nothing is lost by this reshaping.
- Migration is implementation work, sequenced after this decision: the `layer`→`tags` migration and the `category`-as-primary-grouping clarification are follow-ups. The production cutover (the slice that retires `tiles.json`) may interim-seed the required `category` field from the legacy layer to stay unblocked; the `layer`-field removal and themed-sheet querying are separable follow-on slices. Sequencing of those relative to the cutover is a planning detail, not part of this decision.
- This resolves the open question of where the required non-content fields come from once `tiles.json` stops being a runtime source: `category` is seeded from the legacy layer (single primary grouping); `layer` is not seeded as a field (it becomes a tag / stays legacy-only).

Live status and the implementation sequence are maintained in the architecture overview and the Ingestion–Runtime Separation design-of-record. This ADR records the semantic-model decision and its rationale, not live project status.
